# Simulator administration

The environment-configured super administrator owns the staff directory and can manage all customers. Set `CHASE_ADMIN_USERNAME` (defaults to `dianasmith6525@gmail.com`) and a strong `CHASE_ADMIN_PASSWORD` as server-only environment variables. Never place a password in source control or a `VITE_` variable. Set a stable, high-entropy `ADMIN_SESSION_SECRET` as well; changing it invalidates administrator sessions. Redeploy after changing Vercel environment variables. Rotate any password shared in chat.

Administrators created by the super admin see only customers they create or are assigned. Existing customers without an `ownerAdminId` remain visible only to the super admin. In Messages & notices, the super admin can reassign a selected customer to an active administrator; their conversation history and private staff notes follow the customer. Only the super admin can manage staff and global settings. The staff directory controls customer creation, activity generation and message sending individually; administrators retain other customer-management abilities unless separately restricted. Auditor accounts remain read-only.

The support inbox has search and unread/status queues. Saved replies belong to the signed-in administrator. Private notes are omitted from customer API responses. Unread counts and alerts refresh approximately every 30 seconds while the admin page is open. Generated activity is simulated and is labeled in the admin ledger and CSV export.

With `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (or `SUPABASE_SECRET_KEY`), each request reloads the remote snapshot and writes with an `updated_at` compare-and-swap. Competing writes return HTTP 409 and should be retried by the operator; database failures return 503 rather than claiming success. Requests are serialized within a single server process. The code expects `public.chase_simulator_state` with `id`, `state` and `updated_at` columns and server-only access. Without Supabase configuration the simulator uses local JSON, which is not suitable for multiple processes or serverless persistence.

Do not deploy this simulator as real banking software or store real customer data. Before production use, verify access control and persistence against the actual environment, configure the root credentials and session secret, remove known demo accounts with a reviewed backup, and run both `tests/admin-ownership.mjs` (against an isolated test server) and `tests/supabase-concurrency.mjs`. The latter uses a mock PostgREST service and does not replace a live integration test.
